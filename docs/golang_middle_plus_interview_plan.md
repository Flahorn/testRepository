# План собеседования Middle+ Go разработчика

## Цель интервью

Оценить, способен ли кандидат уровня Middle+ самостоятельно проектировать и реализовывать production-grade сервисы на Go, принимать инженерные решения, находить компромиссы между простотой и масштабируемостью, разбираться в существующем коде, работать с конкурентностью, базами данных, API, тестированием и эксплуатацией сервисов.

## Ожидаемый профиль Middle+

Кандидат уровня Middle+ обычно:

- уверенно пишет идиоматичный Go и понимает стандартную библиотеку;
- умеет проектировать HTTP/gRPC-сервисы, API-контракты и внутренние пакеты;
- понимает goroutines, channels, context, race conditions и базовые паттерны конкурентности;
- работает с SQL/NoSQL, транзакциями, индексами и миграциями;
- пишет unit, integration и table-driven тесты;
- способен диагностировать performance-проблемы и production-инциденты;
- понимает observability: logs, metrics, tracing, alerts;
- умеет обсуждать архитектурные trade-off и защищать технические решения;
- может ревьюить код и быть владельцем части сервиса без постоянного контроля.

- Кандидат говорит конкретно: метрики, ограничения, решения, последствия.

### Риски

- Описывает опыт общими словами без деталей.
- Не может объяснить архитектуру сервиса, над которым работал.
- Приписывает себе командные решения, но не показывает личный вклад.

### Практические мини-вопросы

#### Slice aliasing

```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)
fmt.Println(a)
```

Вопросы:

- Что будет выведено?
- Почему?
- Как избежать неожиданного изменения исходного slice?

Ожидаемое направление ответа: кандидат понимает shared backing array и предлагает copy или full slice expression с ограничением capacity.

#### Nil interface

```go
type MyError struct{}

func (e *MyError) Error() string { return "boom" }

func do() error {
    var err *MyError = nil
    return err
}

fmt.Println(do() == nil)
```

Вопросы:

- Что будет выведено?
- Почему error interface не равен nil?
- Как правильно вернуть отсутствие ошибки?

Ожидаемое направление ответа: interface содержит dynamic type и dynamic value; nil должен возвращаться как untyped nil.

### Практический concurrency-сценарий

Нужно обработать 10 000 задач, каждая делает HTTP-запрос к внешнему сервису. Внешний сервис нестабилен, есть rate limit, запросы могут зависать.

Попросите кандидата описать решение:

- ограничение параллелизма;
- context timeout на запрос;
- retry policy с backoff;
- обработка частичных ошибок;
- сбор результатов;
- остановка при отмене;
- метрики и логирование;
- защита от goroutine leaks.

Сильный ответ включает worker pool или semaphore, context propagation, bounded queue, timeouts, idempotency considerations, observability и понятную стратегию ошибок.

## 5. Практическая задача

Выберите одну задачу в зависимости от фокуса вакансии. Для Middle+ важно не только получить работающий код, но и увидеть ход мыслей, декомпозицию, обработку ошибок и тестируемость.

### Вариант A: In-memory rate limiter

Задача: реализовать in-memory rate limiter для API по userID.

Требования:

- лимит N запросов за окно времени T;
- потокобезопасность;
- метод `Allow(userID string) bool`;
- очистка старых записей;
- возможность написать unit tests;
- обсуждение поведения при большом количестве пользователей.

Вопросы после реализации:

1. Какой алгоритм вы выбрали: fixed window, sliding window, token bucket? Почему?
2. Какие edge cases есть на границе окна?
3. Как избежать бесконечного роста map?
4. Как сделать реализацию распределенной?
5. Какие метрики вы бы добавили?

Критерии оценки:

- корректная синхронизация;
- простая и понятная структура данных;
- тесты на границы окна;
- отсутствие глобального состояния;
- понимание ограничений in-memory решения.

### Вариант B: Concurrent fetch with timeout

Задача: написать функцию, которая параллельно запрашивает данные по списку URL и возвращает успешные ответы.

Пример сигнатуры:

```go
func FetchAll(ctx context.Context, client *http.Client, urls []string, limit int) ([]Result, error)
```

Требования:

- ограничить параллелизм параметром `limit`;
- уважать отмену context;
- не допустить goroutine leaks;
- вернуть частичные результаты;
- корректно обработать HTTP errors и timeouts;
- написать table-driven tests с mock server.

Вопросы после реализации:

1. Как остановятся goroutines при отмене context?
2. Что произойдет, если один URL зависнет?
3. Как сохранить порядок результатов?
4. Как добавить retry?
5. Как логировать ошибки без утечки персональных данных?

### Вариант C: Transactional service method

Задача: спроектировать сервисный метод перевода денег между счетами.

Требования:

- проверить существование счетов;
- проверить достаточность средств;
- выполнить debit и credit атомарно;
- защититься от concurrent transfers;
- сохранить audit log;
- вернуть доменные ошибки;
- обсудить тестирование.

Вопросы после реализации:

| Go core и идиоматика | 20% | Понимает язык, ошибки, interfaces, slices/maps, стандартную библиотеку |
| Concurrency | 20% | Уверенно работает с goroutines, channels, context, races |
| Backend и данные | 20% | Проектирует API, транзакции, надежную работу с внешними системами |
| Практическое кодирование | 20% | Пишет простой, корректный, тестируемый код |
| Архитектура и эксплуатация | 15% | Видит trade-off, observability, reliability, scaling |
| Коммуникация и ownership | 5% | Ясно объясняет решения, принимает ответственность |

### Decision guide

- Strong hire: в большинстве блоков 3-4, нет критичных пробелов в concurrency, данных и production-надежности.
- Hire: стабильные 3, отдельные слабые зоны компенсируются опытом и обучаемостью.
- Lean no hire: много ответов на уровне теории, слабая практика с context, транзакциями или тестами.
- No hire: не может объяснить базовые конструкции Go, не видит race conditions, игнорирует ошибки и эксплуатационные риски.

## 14. Красные флаги

- Не понимает nil interface и error handling в Go.
- Не умеет объяснить lifecycle goroutine и риски goroutine leaks.
- Предлагает unbounded goroutines для внешних запросов.
- Игнорирует context cancellation.
- Использует panic для обычных бизнес-ошибок.
- Не пишет тесты или считает их необязательными.
- Не умеет объяснить транзакции и конкурентное обновление данных.
- Считает retries универсальным решением без timeout и backoff.
- Не различает authentication и authorization.
- Не может рассказать о собственных ошибках и выводах.
